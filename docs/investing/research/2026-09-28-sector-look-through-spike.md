# Spike: ETF look-through for sector allocation, and how it combines with #135

_Investigation/prototype spike. Answers the owner's "51.4% Unknown" complaint and decides how ETF look-through combines with [#135](https://github.com/Elmata2/LaVega/issues/135) ("Jev-02: fill the unknown-sector gap with labelled inference") and [#136](https://github.com/Elmata2/LaVega/issues/136) ("Jev-03: OpenFIGI candidate selection"). No code shipped; recommendation only._

## 1. What makes up the Unknown bucket

`resolvePortfolioSectors` (`apps/investing-server/src/sectorResolution.ts`) classifies every priced position through one rule: look up a stored `SectorProfile` by symbol, optionally fall back to `fetchYahooSectorProfile`, and return `UNKNOWN_SECTOR` ("Unknown") if neither answers. `fetchYahooSectorProfile` (`packages/adapters/src/market-data/yahoo/sectorProfile.ts`) reads Yahoo's `quoteSummary` `assetProfile` module and returns `null` whenever that module carries no `sector`/`industry`. There is exactly one door into Unknown, so every cause below funnels through the same `null`.

The dev fixture (`apps/investing-server/src/devFixture.ts`) is 3 plain US/NL stocks (AAPL, MSFT, ASML) and can't reproduce a real Unknown bucket — it isn't representative of the owner's actual T212 holdings. The categorisation below is therefore from the code path plus live Yahoo calls, not from the owner's production data (which this spike is not permitted to read):

- **ETF/fund holdings — the dominant cause, confirmed live.** Fetched `quoteSummary` for `VUAA.L` (Vanguard S&P 500 UCITS ETF) with `modules=assetProfile,quoteType`: `quoteType.quoteType` is `"ETF"`, and `assetProfile` comes back with no `sector`/`industry` at all — just boilerplate (`phone`, empty `companyOfficers`). `fetchYahooSectorProfile` therefore returns `null` for every fund, unconditionally, regardless of how well the symbol resolved. Since a diversified T212/IBKR retail portfolio is typically dominated by one or two broad-market ETFs by value, this single, unconditional gap is the most likely explanation for the bulk of 51.4%.
- **Unresolved or mis-resolved identifiers.** `openFigiProvider.ts` takes `data[0]` from OpenFIGI's mapping response with no candidate ranking (`packages/adapters/src/market-data/identifier/openFigiProvider.ts:74-83`) — this is exactly the gap [#136](https://github.com/Elmata2/LaVega/issues/136) is written against. A `404` leaves the identifier unresolved outright (never priced, so it wouldn't even reach `resolvePortfolioSectors`); an ambiguous multi-candidate response can silently pick the wrong listing, which can resolve to a Yahoo symbol whose `assetProfile` is empty or missing even though the "real" listing would have one.
- **Stock with no Yahoo profile.** `fetchYahooSectorProfile` tries multiple ticker/suffix variants (`getYahooSymbolsToTry`) before giving up. Thinly-covered small caps, foreign OTC listings and some non-US small/mid caps genuinely have no `assetProfile.sector` on Yahoo.
- **Delisted/inactive tickers.** A held, still-priced (via forward-fill) position whose issuer Yahoo has stopped indexing hits the same `null` path.
- **Crypto/other non-equity instruments.** T212 doesn't carry crypto; a bond fund is the realistic case for IBKR/T212 (money-market or aggregate-bond ETFs). Tested live: `AGGG.L` (iShares Core Global Aggregate Bond UCITS ETF) returns `topHoldings.sectorWeightings: []` with `bondPosition: 0.9894`. This is not a data gap — a bond fund genuinely has no equity sector breakdown — and the design in §3 treats it differently from "unknown for lack of data."

One existing piece of evidence that the product already documents this exact gap: `apps/investing-web/src/components/PortfolioSummaryCard.tsx:212-213` prints _"Funds are grouped by their reported sector; underlying holdings are not included."_ directly under the sector panel — i.e. the current behaviour (fund itself has no sector, therefore Unknown) is a known, disclosed limitation, not a bug.

Yahoo `topHoldings` findings, in detail:

- **`sectorWeightings` is a full-fund aggregate, not something derived from the visible top holdings.** For VUAA.L, the 10 listed `holdings` sum to 37.85% of fund value, but `sectorWeightings` sums to 99.98%. Yahoo is reporting a real published aggregate over the whole fund, not just its top-10 list.
- **Taxonomy already matches what the app stores.** `sectorWeightings` uses an 11-bucket scheme (`technology`, `financial_services`, `healthcare`, `consumer_cyclical`, `consumer_defensive`, `communication_services`, `industrials`, `energy`, `utilities`, `basic_materials`, `realestate`) that is GICS's 11 sectors under different labels. Confirmed live: `assetProfile.sector` for AAPL returns `"Technology"`, matching `sectorWeightings`'s `technology` key. No taxonomy bridging is needed beyond a snake_case → Title Case formatter (with two irregular cases: `realestate` → "Real Estate", the rest are underscore-joined).
- **One combined request covers detection + data.** `modules=quoteType,assetProfile,topHoldings` in a single call returns `quoteType.quoteType === "ETF"` (the fund-vs-stock signal) and `topHoldings.sectorWeightings` (the split) together — no extra round trip versus what `fetchYahooSectorProfile` already makes per symbol.
- **Non-applicability is distinguishable from failure.** The bond fund (AGGG.L) returns `sectorWeightings: []` with `stockPosition: 0`, not an error and not an omitted field — code can tell "this fund legitimately has no equity sectors" apart from "the lookup failed."
- **No new auth/consent surface.** This is the same unauthenticated `quoteSummary` endpoint, same crumb/cookie mechanism, same `YahooHttpClient` the app already depends on for `assetProfile` — it sits behind the existing "Yahoo Finance consent" gate with no new terms exposure beyond what the app has already accepted.
- **Rate limits/stability:** no documented limit (it's the same unofficial surface as the rest of the Yahoo integration); the existing `YahooHttpClient` retry/backoff (`RETRYABLE` regex on 429/403/401/502-504) already covers it.

Issuer files and justETF would each need a bespoke, per-issuer scraping adapter (iShares' JSON/CSS shape ≠ Vanguard's ≠ Invesco's), don't obviously beat Yahoo's coverage, and are demonstrably more fragile right now (iShares' own direct CSV export is already broken by their site redesign). This matches the project's standing finding on scraping issuer-adjacent sites (`crawl4ai_eval_lavega` memory: browser scraping loses rows on financial sites; UA string decides access, not headless) — Yahoo's `topHoldings` is the only option of the four that is free, keyless, already-integrated, and confirmed working end to end.

## 3. Design options

**Data-shape change common to every option below:** a position's sector classification stops being a single string and becomes a distribution — a stock is `{Technology: 1.0}`, a fund is `{Technology: 0.39, Financial Services: 0.12, ...}`. `buildSectorExposure` (`packages/core/src/investing/summary.ts:226`) currently multiplies one `marketValue` by one `sector` label; look-through requires it to multiply one `marketValue` by a vector and accumulate into multiple buckets. This is the one unavoidable structural change, independent of which option below is picked.

**Option A — extend `SectorProfileStore` with a fund-level weight profile (recommended, see §4).** Extend `fetchYahooSectorProfile` (or add a sibling `fetchYahooFundSectorWeights`) to request `quoteType,assetProfile,topHoldings` in one call. If `quoteType === "ETF"` (or `"MUTUALFUND"`), store a fund profile (`{ kind: "fund", weights: SectorExposure[] }`) instead of a stock profile; a bond fund with `sectorWeightings: []` stores an explicit empty-weights fund profile, not `null`, so it's cached and never mistaken for an unresolved lookup. `resolvePortfolioSectors`/`buildSectorExposure` explode each position's market value across its stored weights instead of a single bucket. Cached the same way and in the same store as today — no new store type, no new consent flag, just a richer value shape.

**Option B — a hand-curated, in-repo lookup table for a fixed list of common UCITS ETFs**, refreshed manually. Avoids depending on an undocumented Yahoo module continuing to work, but doesn't scale past the curated list, goes stale as funds rebalance (tech weight in the S&P 500 has moved materially over the last two years), and reinvents — with worse freshness — exactly the caching `SectorProfileStore` already does for live data. Rejected: it trades a small, already-mitigated risk (Yahoo module drift, same risk the app already carries for `assetProfile`) for a guaranteed, larger one (silent staleness).

**Option C — resolve a fund's top constituent holdings individually and weight by `holdings[].holdingPercent`, instead of trusting Yahoo's own `sectorWeightings` aggregate.** Rejected on the evidence in §2: `holdings` is capped at 10 names and covers only 37.85% of VUAA by value (confirmed live), so this would silently misclassify the majority of every broad index fund's exposure while costing 10+ Yahoo calls per fund instead of the 1 that Option A needs. Strictly worse on both accuracy and cost.

**How #135 fits.** #135's labelled inference (a `Choice` to Jev/System One over the GICS sector set, using instrument name/description) targets symbols that are priced stocks with genuinely no sector data anywhere — thin OTC names, some non-US small caps, delisted issuers. Look-through is not a replacement for that: it only removes positions that _are_ funds. #135's own precedence ladder (owner correction > provider > inferred > Unknown) already has the right shape for this — a fund's Yahoo-sourced weight profile slots in as a **provider-tier** result (real third-party data, not a guess), sitting above inference exactly like a stock's `assetProfile.sector` does today. Build order matters here: shipping look-through first removes the largest, "for free" (no model cost, no new consent-for-inference toggle, reuses data already fetched under existing consent) slice of Unknown before spending any System One budget on the residual. #135 should then target what's left: real no-profile stocks, plus the resolved-but-not-100%-covered weight inside a fund position when Yahoo's own `sectorWeightings` sums to less than 1 (rare — 6/6 equity ETFs tested summed to ~99.9–100%, but the bond fund is the extreme case, and this should not be silently treated as fully classified).

**How #136 fits.** Not a hard prerequisite. Identifier resolution (OpenFIGI) and sector resolution are independent seams — a position must already be priced (i.e. its identifier already resolved) before `resolvePortfolioSectors` ever sees it, so look-through doesn't call into OpenFIGI at all. #136 is complementary, not blocking: a UCITS ETF cross-listed on multiple exchanges (VUAA trades in London and elsewhere) is exactly the kind of multi-candidate OpenFIGI response #136 targets, so shipping #136 modestly _increases_ how many ETF positions arrive at look-through already resolved, rather than being stuck unpriced upstream. Land in either order; #136 doesn't need to land first.

## 4. Recommendation

**Ship Option A**, sized as two PRs.

**PR1 — fund detection, storage and exposure math (the core change).** Extend the Yahoo sector fetch to request `quoteType,assetProfile,topHoldings` in one call; branch on `quoteType.quoteType === "ETF"`/`"MUTUALFUND"` to store a `FundSectorProfile` (discriminated union alongside the existing stock `SectorProfile` in `SectorProfileStore`); change `resolvePortfolioSectors`/`buildSectorExposure` to resolve and accumulate a weight vector per position instead of one label per position; add a coverage figure to the exposure output (portfolio value resting on a fund's _own_ residual — i.e., the gap when a fund's `sectorWeightings` don't sum to 100%, which is rare but must not be silently absorbed as classified). Tests use the saved live fixture JSON from this spike (`topholdings_*.json`, `combined_AGGG.json`) as recorded responses, so CI has no live Yahoo dependency.

**PR2 — surfacing and consent consistency.** Update `PortfolioSummaryCard.tsx`'s caption (delete "underlying holdings are not included"; state that funds are looked through, and that a small residual may stay Unknown) and label any inferred/estimated component per the codebase's existing rule (never show an estimate as fact). Separately: `/api/investing/summary` in `app.ts` currently calls `resolvePortfolioSectors` with `fetchProfile: sectorProfile` **without** checking `hasYahooConsent` first (unlike `/api/prices/sync` and the benchmark-search route, which do gate on it at `app.ts:357-358` and `app.ts:512-513`). Look-through adds a second Yahoo-backed sector fetch path; worth closing this consent gap in the same PR rather than shipping a second ungated call.

**Expected reduction:** not quantifiable against the owner's actual 51.4% without his real holdings (unreadable per this spike's constraints), but structurally: this spike confirms 7/7 tested UCITS/ETF tickers (US large-cap, world, EM, Nasdaq-100, bond) return usable Yahoo data, and a fund is _unconditionally_ Unknown today regardless of resolution quality. Given ETFs are typically an owner's largest position(s) in a T212/IBKR portfolio by construction, this plausibly explains most of the 51.4%.

**Risks:** (1) Yahoo's `topHoldings` module is unauthenticated/unofficial — same risk class the app already accepts for `assetProfile`, not a new one. (2) Fund weights should be refreshed on a cache TTL (funds rebalance roughly quarterly; per-request freshness is unnecessary and would multiply calls). (3) The `buildSectorExposure` signature change (string → vector) is a real behavioural and type change with its own test surface — size and review it as its own unit, not folded into the UI change. (4) A fund whose Yahoo weights don't sum to 100% must add its residual to a labelled/coverage bucket, not silently round up to fully classified — this is the one place look-through itself needs the "never show an estimate as fact" discipline, independent of #135.
