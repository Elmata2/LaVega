# Research: charting libraries

Resolves [#21](https://github.com/Elmata2/LaVega/issues/21). Feeds [#22](https://github.com/Elmata2/LaVega/issues/22) (decide charting library) and the [Investing stack & platform](https://github.com/Elmata2/LaVega/issues/15) map.

## Question

Which charting libraries can serve the investing dashboard's chart inventory, and how do they compare on license, bundle size, feature fit and accessibility?

## Chart inventory (source: [#16 resolution](https://github.com/Elmata2/LaVega/issues/16#issuecomment-5216775088))

Per #16's closing comment, v1 is exactly three chart types, EUR-converted, no candlestick/OHLC anywhere (daily EOD price data only):

1. **Portfolio value vs. benchmark** — multi-series line (portfolio + optional benchmark overlay), time-range switcher (1M/6M/1Y/YTD/All), hover tooltip, entity filter (combined by default).
2. **Allocation donut** — by instrument / by entity (toggle), snapshot only (no time axis), entity filter.
3. **Per-position price line** — single-series daily EOD line, trade markers (buy/sell) + dividend markers, hover tooltip.

Not required: candlestick/OHLC, zoom/pan/brush, full per-entity view-switching. Candlestick is explicitly not *permanently* ruled out — if a future data source adds real OHLC, this is a re-run of #21/#22.

**Practical read:** the field is multi-series/annotated line charts + a pie/donut, with tooltips. That's a much smaller bar than "financial charting library" — it widens the field to general-purpose libraries and makes TradingView `lightweight-charts`'s candlestick specialization mostly wasted spend for v1.

## Standing constraints (from the [investing-stack-map](https://github.com/Elmata2/LaVega/issues/15))

- LaVega is **AGPL-3.0**, self-hostable. A self-hoster must never need a LaVega account, cloud, or API keys — this research treats **license compatibility with self-hosted redistribution** as a hard gate, not a nice-to-have.
- `apps/investing-web` is decided ([#17](https://github.com/Elmata2/LaVega/issues/17)): React 18 + Vite, **no SSR**, React Router, shadcn/ui (Tailwind + Radix) — a deliberate divergence from `apps/web`'s hand-written CSS. SSR compatibility is therefore *not* a filter here.
- "Prefer boring, conventional, strongly-typed tools" is an explicit tiebreaker — agent harnesses (Claude Code, etc.) drive conventional layouts better than clever ones.
- The personal side (`apps/web`) uses **no chart library** — hand-rolled inline `<svg>` in `apps/web/src/views/Overzicht.tsx` (`Sparkline`, `CashflowMiniChart`) and `Forecast.tsx`. Every chart there is `role="img"` + a Dutch `aria-label`, and none of them are interactive (no tooltips exist in the personal side today) — this research's tooltip requirement is new ground, not a port.

## Method

Primary sources only: each package's own `LICENSE`/`LICENSE.md` file on GitHub (not npm's `license` metadata alone, which can be wrong or absent), each project's own docs for feature claims, and `bundlephobia.com`'s API (built on the published npm tarball) for gzip'd size, cross-checked against `registry.npmjs.org`. All fetched 2026-08-07. Sizes are for the "obvious" install, not a hand-tuned tree-shaken build, except where noted.

LaVega distributed to a self-hoster running a business, or a future paid hosted tier, is unambiguously commercial use. **Not shippable in an AGPL, freely-self-hostable product** — excluded outright, not scored above.

## License-gate summary

Everything actually scored above is MIT, Apache-2.0, or ISC — all OSI-approved, permissive, and compatible with AGPL-3.0 redistribution; a self-hoster incurs no obligation beyond keeping the library's own copyright notice in `node_modules` (standard npm practice). The one real flag in the survey is **`lightweight-charts`**: license-compatible, but it carries a **mandatory, permanent TradingView attribution/link requirement on every self-hosted instance** — a product-level constraint (forced branding in LaVega's own UI) more than a legal blocker. Combined with candlestick — its whole reason for existing — being explicitly out of scope for v1, it's excluded from the shortlist.

## Shortlist: two libraries to prototype

1. **Recharts** — the "ship it" default. Native `PieChart` (donut) and `LineChart` (multi-series + tooltip) cover chart #1 and #2 directly; markers for chart #3 are a well-documented `ReferenceDot`/`Scatter` composition, not a workaround. MIT, zero attribution. SVG/DOM output keeps the app's existing `aria-label` accessibility convention alive without a canvas-to-screen-reader gap. Biggest React charting community by a wide margin — the best fit for the stack map's "boring, conventional, agent-harness-friendly" tiebreaker. Cost: heaviest of the SVG options (147.5 KB gzip, `redux` internals as of v3).
2. **visx** — the "keep control" counterpart, deliberately not a second flavor of the same thing. Same MIT/no-attribution/SVG-DOM-a11y profile as Recharts, but composable low-level primitives (`@visx/shape`, `@visx/scale`, `@visx/xychart`) instead of a monolithic component API — smaller per-feature footprint (~50 KB gzip for a full tooltip-enabled xy chart via `@visx/xychart`) and more room to match shadcn/ui's editorial aesthetic precisely, at the cost of writing more of the marker/annotation wiring by hand. Effectively "D3 direct" with the scale/interpolation math (which `Overzicht.tsx`'s `CashflowMiniChart` currently hand-writes) done for you, rather than from scratch.

**Runner-up, not shortlisted:** ECharts. It has the single best native fit for chart #3's trade/dividend markers (`markPoint`/`markLine` are purpose-built for exactly this) and native candlestick if #16's "not permanently ruled out" caveat ever fires — genuinely the strongest pick if annotation density or a future OHLC requirement turns out to matter more in prototyping than expected. Held back from the top two only by canvas rendering breaking the app's existing SVG+`aria-label` accessibility pattern (partially, not fully, mitigated by ECharts' own `aria` component) and its much heavier default bundle. Worth a third prototype if either Recharts or visx stalls on the marker requirement in #22.

**Not shortlisted, with reasons:** Observable Plot (no native donut mark — a hard gap for chart #2, and not React-idiomatic); Nivo (same profile as Recharts/visx but no differentiated advantage, plus `@react-spring` animation weight neither chosen option needs); Chart.js (canvas a11y gap without ECharts' mitigating aria module, and markers require a bolt-on plugin rather than a core feature); `lightweight-charts` (attribution burden, and its specialization — candlestick — is exactly what v1 doesn't need); uPlot (no pie/donut primitive at all — would still need a second library for chart #2); Victory (functionally close to Recharts/visx with no distinguishing edge and softer momentum lately); D3 direct (all the effort of the incumbent hand-rolled approach, for three chart types plus new tooltip interactions that don't exist anywhere in this codebase yet — too much net-new code for the timeline); hand-rolled SVG (the incumbent already does this for the personal side, but has never built a tooltip once — extending it to three interactive chart types plus a donut is reinventing what Recharts/visx already give for free, with no license reason to avoid them).
