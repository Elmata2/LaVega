## Findings considered and not yet planned

These came out of the same perf review but were not written up as plans —
flagged for a future round if the user wants them pursued:

- **Bounded concurrency for Yahoo Finance price-sync requests**
  (`apps/investing-server/src/priceOrchestrator.ts`): requests are fully
  sequential, one symbol at a time. Yahoo has no documented hard concurrency
  cap (unlike Trading 212's cursor-paginated order history, which genuinely
  must stay sequential — see `packages/adapters/src/brokers/trading212/adapter.ts:546`).
  Medium effort, medium risk — needs a shared rate limiter instead of the
  current fixed pace, and care around 429 behavior. Worth doing only if cold
  (never-synced) portfolios are still slow after Plan 001 lands.
- **Retry backoff cost on flaky/rate-limited symbols**
  (`packages/adapters/src/market-data/yahoo/http.ts:2-4`, `85-96`): up to 3
  retries at `1.5s * 2^attempt` (up to 6s) each; because sync is sequential,
  one bad symbol stalls the whole queue behind it. Mostly resolved in
  practice if the concurrency finding above is picked up; not worth doing on
  its own.
- **No session-level "already synced recently" skip on the frontend** for
  price sync (`apps/investing-web/src/app.tsx:1077`,
  `apps/investing-web/src/lib/priceSync.ts`) — the broker-sync side already
  has this (`packages/adapters/src/brokers/scheduledSync.ts:95-96`, 24h
  cooldown unless `force`), price sync does not. Low priority once Plan 001
  lands, since the server-side cache check already makes a warm re-sync
  cheap; this would only save the round-trip itself.
